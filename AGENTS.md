# [AGENTS.md](http://AGENTS.md)

## Project Overview

A clinical research team website built with Next.js (App Router), Sanity CMS, and Tailwind CSS. Data sources include PubMed, ClinicalTrials.gov, and OpenAlex with cached results in `runtime/`.

## Development Ethos

- Prioritize maintainability.
- Optimize for ease of use by nontechnical research staff.
- Favor stable patterns that minimize breakage when dependencies or frameworks update.
- Prefer well-supported Next.js/Sanity patterns over custom or experimental approaches.
- Keep editable content in Sanity when staff need to change it; avoid hard-coded copy.
- After major changes, review and update this file (`AGENTS.md`) for consistency.

## Key Paths

- `app/` pages/layouts and API route handlers (`app/api/**/route.js`)
- `app/admin/` admin hub and `/admin/*` entry points
- `app/components/` shared UI components
- `app/llms.txt/` LLM summary endpoint
- `app/markdown/` markdown endpoints (used via `.md` URLs)
- `lib/` data clients, caching, and shared helpers
- `sanity/` Sanity Studio config and schemas
- `scripts/` maintenance/migration scripts
- `runtime/` generated caches and lock/cancel files (do not edit by hand)
- `dist/` build output (do not edit)

## Conventions

- Server components by default; add `"use client"` only when needed.
- Keep data-fetching helpers in `lib/` and call them from pages or route handlers.
- Use Tailwind classes for styling unless a nearby component already uses `styled-components`.
- Node scripts are ESM (`"type": "module"`); use `import` syntax.
- Prefer `lib/sanity.js` for general reads/writes; `lib/sanity/client.js` is a no-CDN client for maintenance checks.
- Public navigation and dense link collections intentionally use `prefetch={false}` in several places to limit background requests and Vercel invocation noise; do not re-enable broad automatic prefetching without checking production impact.

## Maintenance Mode

- Settings live in Sanity (`siteSettings.maintenanceMode`) and are read via `lib/sanity/client.js`.
- Under-construction flow uses `proxy.js`, `/under-construction`, `/api/maintenance`, and `/api/auth` (cookie `site-auth`).
- If you change this flow, keep it simple and stable so staff can toggle maintenance mode without dev help.
- During maintenance, allowlisted paths still resolve: `/llms.txt`, `/sitemap.xml`, `/robots.txt`, and markdown endpoints (`/markdown/*` and `*.md`).
- `proxy.js` intentionally excludes API/static asset requests from the matcher to reduce Vercel middleware invocations; keep the matcher tight if you add new public asset types.
- The proxy's maintenance fetch is hardened for non-OK and non-JSON responses, especially on preview deployments; preserve that defensive behavior if you refactor it.

## Contact & Email

- Contact form posts to `app/api/contact/route.js` and routes via Sanity `contactRouting`. Approval admins change each reason's target email (plus `siteSettings.contactEmail` and `.replyToEmail`) at `/admin/people`; the reasons' wording and order stay in Studio.
- Email delivery uses `lib/email.js` (Resend), optional reCAPTCHA, and PDF-only attachments (6MB max).
- Keep error states and form fields straightforward for nontechnical users.

## Studies and Site Teams

- Studies are coordinated out of separate sites (Victoria Hospital, University Hospital and St. Joseph's Health Care), each with its own PIs, coordinators and startup fees. A study has one **team per coordinating site** in `trialSummary.siteTeams` (site reference, team `status`, PI reference or free-text name, `contact`, `acceptsReferrals`) and a separate `recruitmentSites` list of places where patients are enrolled (the hospitals, the Kidney Care Centre clinics and dialysis unit at Westmount, and the regional dialysis satellites in Chatham, Goderich, Hanover, Owen Sound, Sarnia, Stratford, Tillsonburg and Woodstock). Coordinating sites are `site` documents with `coordinatesStudies`; enrolment places have `recruitsPatients`. Every active `site` also appears in the subscriber "Location of practice" field (`buildSiteOptions` in `lib/sites.js`), satellites included. The app's queries list only sites whose `active` is true.
- Each site starts up on its own, so a team has its own `status` (`enrolling`, `not_yet_enrolling`, `closed`). The study-level `status` stays the public headline. A team that is not enrolling is shown as "starting soon", its contact is not shown, and it takes no referrals.
- Read teams only through `lib/studyTeams.js` (browser-safe): `resolveStudyTeams(study)` for query results (document shape, built by `studyTeamsProjection()` in `lib/sanity.js`) and `resolvePayloadTeams(record)` for the Study Manager, submissions and drafts (payload shape, `STUDY_STAFF_PROJECTION`). Both synthesize one team from the legacy single `principalInvestigator` / `localContact` / `acceptsReferrals` fields on records the migration has not reached, so nothing else reads those fields. Writers never set them: `buildPatchFields` writes `siteTeams` and `recruitmentSites`, `buildUnsetFields` removes the legacy fields, and `buildTrialSummaryDoc` is the one create builder for approvals and admin direct publishes. Team `_key`s are opaque (Studio assigns its own); a team's identity is its site reference, and `validateSiteTeams` enforces one team per site, a PI per team and a contact email before referrals.
- `npm run migrate:site-teams` (dry run, one line per study) converts each study's legacy fields into one team, inferring the site from the PI's published `researcher.primarySite` when it coordinates studies (a PI outside the roster is placed with `SITE_TEAMS_PI_SITES`, "PI name = site" pairs; the workflow's `pi_sites` input); `-- --apply` writes it, `-- --apply --remove-legacy` then unsets the legacy fields and refuses while any study lacks a team with a PI. Set the site flags and the PIs' primary sites in Studio and redeploy Studio before running it. Submissions and drafts are not rewritten: `normalizeStudyPayload` converts a legacy payload whenever it is read. Studio shows the legacy fields only on a study without teams, and the per-team site rule is a warning until the legacy fields are removed. The migration was applied on 2026-10-04 (69 studies, one team each: 61 from the PI's primary site, 7 by override, Kristin Clemens' studies to St. Joseph's Health Care and Sarah Shalhoub's, Ephraim Tang's and Alp Sener's to University Hospital); TREAT-COVID had no PI on record and was deleted in Studio on 2026-10-05, after which `--remove-legacy` unset the legacy fields on all 68 studies. The `trialSummary` documents no longer carry them; the schema still declares them and `lib/studyTeams.js` still falls back to them because older submissions and drafts keep legacy payloads, so removing the schema fields and the fallback branches is the remaining cleanup.
- Referrals are counted per site, so the clinician picks the team when more than one takes referrals: the study page passes only `{ key, label }` per accepting team to `ReferralForm`, the request carries `teamKey`, and `/api/referral` resolves the contact with `pickReferralTeam` over the server-only `trialCoordinator` projection (a key never routes to a team that is not accepting). The receiving site is stored on the `studyReferral` (`team`) and named in the coordinator's email subject and the clinician's confirmation. The route also uses `claimSecurityRateLimit` (per origin and aggregate), skipped only when no write token is configured.
- Public queries project a team contact only when `displayPublicly` is true (GROQ `select`) and compute `canReceiveReferrals` server-side, so hidden coordinator emails never reach the browser or the markdown endpoints; list pages project no contact at all. Study update emails still mail each accepting team's contact directly (one "Refer a patient" button per team, labelled by investigator and site when a study has several teams) and show where patients can be seen.
- Study Manager (`/trials/manage`, `/admin/studies`) and the approval editor share `app/trials/components/StudyTeamsFieldset.js` and `studyFormModel.js`. The manage GET returns each study's latest pending submission; a coordinator's form starts from it ("Changes by X are awaiting approval. Your edits build on them"), sends `basedOnSubmissionId`, and the PATCH returns 409 when a newer pending submission exists. An admin's direct publish supersedes the pending submissions for that study; rejecting a submission reinstates the one it superseded. The approvals list, the approval editor and the approval email show a change summary (`summarizeStudyChanges`) grouped by team, and every write that changes a study calls `revalidateStudyPages`. The duplicate-NCT dialog opens the existing study and carries the typed team across, which is how a second site joins a registered study.
- Access control is unchanged: any coordinator can edit any study, and approval admins review everything. If the sites later need hard separation, add per-site coordinator lists and match team panels by `site._ref`.

## Study Updates

- Subscriber management uses `app/api/updates/manage/route.js` with `manageToken`.
- Only published `updateSubscriber` records are real subscribers. `writeClient` uses API version `2024-01-01`, whose default raw perspective also returns Studio drafts (`drafts.<id>`), so every send, count and admin list query uses `DELIVERABLE_SUBSCRIBER_FILTER` or `PUBLISHED_SUBSCRIBER_FILTER` from `lib/updateSubscriberStatus.js`. Before this rule a subscriber with an unpublished Studio edit got every email twice, and a record created in Studio but never published was emailed. `tests/subscriberDeliveryFilters.test.js` fails when a new query names `_type == "updateSubscriber"` without the filter, unless its file is listed there with the reason it handles drafts itself.
- A manage token or signup email can match a record and its Studio draft, because drafts copy every field. `pickPublishedSubscriber` settles on the published record: the preference link (`app/api/updates/manage/route.js`) reads it and writes each change to it and to its draft, so publishing an old draft cannot undo an unsubscribe, and falls back to a record that only exists as a draft. Signup (`lib/subscriberSignup.js`) only recovers a published record; when the address is held only by an unpublished draft, it creates the published record under the draft's id and token (unless something else is already published under that id), so a later Studio publish updates that record instead of adding a duplicate.
- Admins manage the mailing list itself at `/admin/people` (see People & Email Lists); `/admin/updates` links there instead of listing subscribers.
- Dispatch runs via `/api/updates/study-email/dispatch`; scheduled sends are triggered from `.github/workflows/study-email.yml`, which runs daily at 11:00 UTC (morning Eastern time) and lets the route enforce only the configured nth weekday from Sanity.
- Requires `SANITY_API_TOKEN` to record send status.
- Interest area options come from active `therapeuticArea` docs; subscribers store `interestAreas` references plus `allTherapeuticAreas` for opt-in-all.
- `siteSettings.studyUpdates` includes `scheduleOccurrence` and `scheduleDayOfWeek` so staff can choose schedules like 1st Monday.

## Trial Matching Assistant

- Detailed feature handoff lives in `docs/trial-matching-assistant.md`.
- Public entry point is the floating widget mounted in `app/layout.js`; it appears across public pages, auto-opens on the homepage, and talks to `app/api/trials/match/chat/route.js`. The widget supports optional **voice input** via the browser Web Speech API (microphone button) where available.
- The widget stays available across client-side navigation, can be minimized to a launcher, and currently hides itself on `/admin`, `/login`, `/protected`, `/trials/manage`, `/trials/approvals`, `/updates/admin`, and `/under-construction`.
- `/trials/find` remains a lightweight fallback/info page that points visitors back to the floating widget and is not the primary experience.
- `/trials/find` is intentionally noindexed and no longer appears in the sitemap as a primary public entry point.
- Global availability is controlled in Sanity via `siteSettings.trialMatchingAssistant.enabled`. Missing values read as disabled, so older `siteSettings` documents must be backfilled explicitly.
- The assistant uses its own optional Sanity LLM settings at `siteSettings.trialMatchingAssistant.llmProvider` and `.llmModel`. These override trial-summary settings so the public chat can use a cheaper deterministic model while publication summaries and classification use stronger models. Provider API keys are server environment variables only and must never be stored in Sanity.
- The assistant uses an LLM for conversation, structured profile extraction, and **study shortlisting**: `generateTrialMatchStudyRanking()` in `lib/summaries.js` runs a second model call with the patient profile plus per-study title, lay summary, and inclusion excerpts; output is **nondeterministic** and phrased as “may fit” / coordinator review. If that call fails, the API falls back to rule-based `rankTrialMatches()` in `lib/trialMatcher.js`, which now relies on title/summary/inclusion-text heuristics only.
- The chat LLM also receives truncated **inclusion** lines from Sanity (`trialSummary.inclusionCriteria`) plus the public study catalog during the conversational turn. Keep the structured chat extraction turn deterministic (`temperature: 0`) and with enough output budget for the full required `patient_profile` JSON. Gemini 3.x models on OpenRouter should use minimal excluded reasoning for trial matching; when changing models, verify compact inputs such as `GFR 40 ACR 45 IgA` do not finish with `length`.
- The in-memory patient profile now supports structured **numeric urine protein** data (`patient_profile.urineProtein`) alongside booleans. The backend can parse user-reported **ACR/PCR** values, assumes **mg/mmol** when a user gives ACR/PCR without units, performs exact same-assay unit conversion (`mg/g`, `mg/mmol`, `g/g` for PCR), and stores approximate cross-assay estimates for ACR↔PCR only as soft screening context.
- The same structured profile also supports **24-hour urine protein excretion** (`mg/day`, `g/day`). The matcher can compare explicit study thresholds like `proteinuria >= 1 g/day` directly, and it may derive approximate PCR/ACR context from timed protein excretion for soft screening only.
- Near-threshold urine protein values should remain conservative: exact or estimated ACR/PCR close to a study cutoff should keep a study in `possible` rather than causing a hard exclusion. Coordinator review still confirms final eligibility.
- If a likely study depends on a urine protein threshold and the user has not yet provided a quantitative value, the assistant may ask one focused follow-up for a recent quantitative value (`ACR`, `PCR`, or `24-hour urine protein`). This can apply when proteinuria was mentioned qualitatively or omitted entirely. If no number is available, do not loop on the same question; keep the study `possible` and let coordinator review confirm the threshold.
- Only studies with `status == "recruiting"` participate in the assistant.
- When the **fallback** matcher runs and at least one `match` or `possible` result exists, the API returns at most two **`insufficient_info`** rows so broad studies do not crowd the list.
- Patient characteristics must remain ephemeral. Do not store transcripts or patient details in Sanity or email them.
- Use existing public study copy in results (`title`, `laySummary`, and `inclusionCriteria`). Do not surface clinician-only communication fields in the assistant.
- The public API in `app/api/trials/match/chat/route.js` applies identifier redaction to messages and free-text profile fields, rejects oversized bodies, and uses durable per-origin plus aggregate rate limits through `lib/securityRateLimit.js`. Do not replace these controls with process-local counters.
- A turn that produces results is two requests. The chat route answers `rankingPending: true` with an interim reply listing the captured profile ("Checking the recruiting studies for: …", `buildRankingPendingReply` in `lib/trialMatchRanking.js`) instead of ranking inline; the widget shows it, then posts the same transcript and profile to `app/api/trials/match/rank/route.js`, which runs the shortlist and `generateTrialMatchStudyRanking()` (rule-based fallback) and returns the results with the fixed closing reply. Both routes share `prepareTrialMatchRequest` in `lib/trialMatchApi.js`, which claims the rate limits, reads the body and loads the Sanity context concurrently; the per-origin budget is 30 requests per 15 minutes because of the second request. Measured on 2026-10-05 the chat turn takes 3–5 s and the ranking 7–9 s on GPT-6 Luna, so keep the handover: the person sees the acknowledgement after the chat turn rather than after both.
- Ranking runs at low reasoning effort (`TRIAL_MATCH_RANKING_REASONING`). Medium measured 10–17.5 s per ranking on GPT-6 Luna against 7–9.5 s at low with the same studies surfacing; minimal was no faster than low on that model. The ranking prompt sends studies under short aliases (`S1`, `S2`, …) so the model does not echo 36-character Sanity ids, asks for reasons under 20 words, and drops a study the model lists twice. Output tokens dominate the wait (roughly 50–90 tokens a second on these calls), so keep structured outputs small when changing these prompts.
- GPT-6 Luna generates output about half as fast as GPT-5.6 Luna on these calls (same shortlist: ranking 10–17 s against 7.7–8.5 s at medium effort). `siteSettings.trialMatchingAssistant.llmModel` exists so the assistant can run on a faster model without touching the summary pipeline.
- The Study Manager and approvals editors no longer collect assistant-specific matching metadata. Do not reintroduce staff-only matching fields unless product requirements change.
- If the widget is missing locally, check the current dataset's `siteSettings.trialMatchingAssistant.enabled` value before debugging UI code. Existing documents can have `trialMatchingAssistant: null`, which disables the widget.

While disabled, keep public digest navigation/archive routes, discovery metadata, new subscription choices, and general subscriber delivery unavailable; imports, admin diagnostics, and explicitly configured pilot or update-testing delivery remain available for development.

The send route still requires that automatic approval as a safety gate. `siteSettings.researchDigest.maxPapers`, `.minPriorityScore`, and `.automaticSelection` override those defaults, but `maxPapers` is clamped to `RESEARCH_DIGEST_MAX_PAPERS_CEILING` (3) — a subscriber can never receive more than three papers in a day. Selection draws from a rolling pool: today's papers plus qualifying papers deferred within `carryoverDays` (default 7), so a strong paper that loses its slot is not discarded permanently. A paper that has already shipped never re-enters the pool.
- `siteSettings.researchDigest.pilotMode` defaults to disabled. When explicitly enabled, sends go only to `researchDigest.pilotRecipients` plus `RESEARCH_DIGEST_PILOT_EMAILS`; if none are configured, the send route fails closed.
- Scheduled publication sends run from `.github/workflows/publication-newsletter.yml`; the workflow runs daily at 11:00 UTC (morning Eastern time) and the route checks only the configured nth weekday in Sanity before sending.
- `siteSettings.publicationNewsletter` includes `scheduleOccurrence` and `scheduleDayOfWeek` for staff-managed timing.
- The research digest workflow runs weekdays from `.github/workflows/research-digest.yml`: import and automatic selection at 10:00 UTC, then send at 13:00 UTC. Workflow concurrency prevents the send run from overtaking a delayed import.

## Publications RSS Feed

- `/publications/feed.xml` (`app/publications/feed.xml/route.js`) is an RSS 2.0 feed built from the public PubMed cache (`lib/publicationFeed.js`), listed for autodiscovery from `/publications`.
- It includes non-excluded publications that have a lay summary and were published within the last `PUBLICATION_FEED_WINDOW_DAYS` (60) days, capped at `PUBLICATION_FEED_MAX_ITEMS` (50), newest first.
- Staff connect this feed to Zapier ("RSS → LinkedIn company update") and possibly LinkedIn's native Page RSS import, where each new item becomes one social post. GUID and link come from the cleaned DOI (falling back to PMID) via `getFeedItemIdentity()`; DOI wins over PMID because a record can start DOI-only and later merge with a PubMed record that adds a PMID. Never change that identity scheme, or a paper's GUID/link will change and it will be reposted.
- The `.xml` extension keeps the route outside the maintenance proxy's redirect (`proxy.js`'s matcher already excludes `.xml` paths).
- `/api/pubmed/revalidate` revalidates the feed alongside `/publications` after each PubMed refresh so new papers reach the feed promptly.

## Social Posting (Buffer → X, admin-approved)

- Nothing is posted by default. Approvers choose which new papers to post about, draft and edit the text, and queue it in Buffer at `/admin/social` (approvals admins; API `app/api/social/posts/route.js`). A queued post can be undone until Buffer publishes it.
- Flow: after the PubMed refresh, the final step of `.github/workflows/pubmed-refresh.yml` calls `POST /api/social/dispatch` (CRON auth). It records each new feed paper as an `available` `socialPost` with its lay summary and no post text, then emails approvers once about the papers that became `available` and were never in an email (subject `N new publication(s) you could post about`; title, journal, date, team members, lay summary and paper link). There are no reminders, the email is skipped when nothing is new, and papers are marked notified only after a confirmed send (the idempotency key is unchanged). Nothing is drafted or sent to Buffer at this stage, so there is no cap on new papers per sync; a large sync only means a longer email. `{ "seed": true }` still marks the current unrecorded feed items `seeded` so they are never offered, `dryRun` previews without writing, and the route throws when the publication cache cannot be read.
- Items come only from `selectFeedPublications(readCache()?.publications || [])` with `identity.guid`/`identity.link`, so X and the RSS feed agree on which papers (the GUID). The X post itself links to an investigator's profile (see below), while the RSS feed's link and GUID stay the paper's DOI (PMID fallback), and the approver email still shows the DOI link. Never derive GUIDs another way.
- The email deliberately has no decision links, because Outlook Safe Links opens links automatically. Every action happens in the portal.
- Statuses: `available` (paper offered, no post) → `draft` ("Create post") → `sending` → `queued` ("Queue in Buffer") → `published`. Also `removing` (undo in progress), `dismissed` ("Not posting"; "Restore" returns it to `available`) and `seeded`. Drafts can be saved, regenerated, discarded back to `available`, or dismissed (which discards the draft in the same write). Legacy `pending` and `skipped` records read as `available` and `dismissed` until `npm run migrate:social-posts -- --apply` converts them (dry run by default; it prints counts only, fills `laySummary` from the cache, and writes one revision-guarded transaction).
- Every approver action reads the record and writes with `patch(id).ifRevisionId(rev)`; a 409 becomes "already being changed, reload". Queue and undo first lock the record in `sending` or `removing` that way, so each paper posts at most once; the writes that record Buffer's answer follow while the lock holds. The transitions live in `lib/socialPosting.js`; `createSanitySocialPostStore` supplies `transition` (guarded) and `update` (the follow-up write).
- Queue: validates and saves the text, resolves the X channel, then calls Buffer `createPost` with `mode: addToQueue`, which publishes at the X channel's next posting slot. Success gives `queued` with `bufferPostId`, `dueAt` and `queuedBy`. A definite Buffer rejection returns the post to `draft` with `lastError`. An ambiguous result (network error, timeout, 5xx, unreadable response) stays `sending`, shows as "Buffer result unknown — check the Buffer queue", and is never retried automatically.
- Undo: locks `queued` → `removing`, then reads the post from Buffer. `sent` becomes `published` (with `sentAt` and `externalLink`) and cannot be undone here; delete it on X. `sending` goes back to `queued` ("check again in a minute"). Not found returns the post to `draft` ("It was no longer in Buffer"). Any other Buffer status (`scheduled`, `draft`, `needs_approval`, `error`) is deleted with `deletePost`, and success returns the post to `draft` with its text, `unqueuedBy` and `unqueuedAt`. A definite error from either call returns the post to `queued` with `lastError`. An ambiguous delete stays `removing` and shows as needing a check. An unclear status read also returns the post to `queued`, because reading changes nothing in Buffer. Undo works even when the Site Settings switch is off.
- `sending` and `removing` records show under "Needs checking". Staff check the Buffer queue first; to clear the record, delete it in Studio (its fields are read-only), and a paper still in the feed comes back as `available` on the next sync.
- Each portal load checks up to 10 `queued` posts in Buffer (`refreshQueuedSocialPosts`): `sent` becomes `published`, Buffer's `error` message becomes `lastError`, and a missing post gets "Not found in Buffer; it may have been deleted there". Failures only add a `bufferStatusWarning`. Each check is one Buffer request, so keep the limit low.
- Drafting ("Create post", "Regenerate") calls `generateSocialPostText` in `lib/summaries.js` through `composeSocialPostDraft` in `lib/socialPostDrafting.js`. The provider and model are `siteSettings.llmProvider || LLM_PROVIDER || 'openrouter'` and `siteSettings.llmModel || LLM_MODEL || DEFAULT_LLM_MODEL`, like the SEO refresh. Drafting runs only on these explicit actions; nothing is drafted automatically.
- The approver's requirements, enforced by the prompt (`SOCIAL_POST_SYSTEM_PROMPT`) and checked in code: every listed team member (investigator) must be named in the post, identified as one of the team's investigators using the Team Name in Posts setting (e.g. "London Kidney investigators Amit Garg and Arsh Jain found …"); no first person ("our", "we", "us"); and no journal name. The model also states the main finding in plain language faithful to the lay summary, with no hype, advice, emojis, hashtags, handles or links (the link is appended after). OpenRouter requests use low reasoning effort (`SOCIAL_POST_REASONING`) with an 800-token content budget plus `REASONING_TOKEN_HEADROOM`.
- Whether the paper has authors beyond the team is passed to the model as a yes/no/unknown flag, never a count. `computeHasOtherAuthors(authors, teamMembers)` in `lib/socialPosting.js` compares the cached publication's `authors` (display strings from PubMed/etc., e.g. "House AA") against the record's `teamMembers`: `null` (unknown) when `authors` is missing or empty, otherwise `authors.length > teamMembers.length`. `buildSocialPostRecord` stores the result as `hasOtherAuthors` (boolean field, omitted rather than written when unknown). `buildSocialPostPrompt` adds a line right after the investigators line ("Other authors on this paper besides these `<team>` investigators: yes/no/unknown"), and the default prompt's rule (a) tells the model to add "and colleagues" after the names when there are other authors, and not to when there are none or it is unknown. The template fallback (`buildXPostText`) does the same when `hasOtherAuthors` is `true` (`composeSocialPostDraft` passes `hasOtherAuthors === true` to it); the byline-shortening for a long list of team members (first three plus "and colleagues") never doubles up "and colleagues" when both apply. The portal shows "· plus other authors" on the team members line when the flag is set.
- The post ends with a link to one investigator's profile, anchored to the paper (`<site>/team/<slug>#<paperAnchor>`), because X cannot hyperlink names and shows the profile's preview card instead. Who gets it: the paper's first author when they are a team investigator with a profile (`first-author`, regardless of recent posts); otherwise a random team investigator with a profile not featured in the last `SOCIAL_POST_SPOTLIGHT_WINDOW_DAYS` (30) days (`rotation`); otherwise, when all were, the one featured longest ago, ties at random (`least-recent`). When no team investigator on the paper has a profile slug, the post links to the paper (`link`) as before. Profile links need `SITE_URL` (or `NEXT_PUBLIC_SITE_URL`) set to the site's public https address; when it is unset, so `getSiteBaseUrl()` falls back to `http://localhost:3000`, or is not https, or points at a local host (`localhost`, `*.localhost`, `127.x.x.x`, `[::1]`, `0.0.0.0`), posts link to the paper. "Featured" is read from post text, not a stored id, so a hand-edited link counts: a `draft`, `sending`, `queued`, `removing` or `published` record whose `text` has an http(s) URL with path `/team/<slug>` (slugs compared case-insensitively), dated `sentAt || dueAt || queuedAt || draftedAt` (an upcoming `dueAt` counts), excluding the post being drafted. Pure logic is `collectRecentSpotlights`, `chooseSpotlightResearcher`, `buildProfilePaperLink` and `describeSpotlightReason` in `lib/socialPosting.js`; `resolveSocialPostSpotlight` in `lib/socialPostingStore.js` loads researchers with a slug plus the post history, and the route passes its link to `composeSocialPostDraft` (`link` overrides `post.link` in both the AI draft and the template). If choosing fails, the route logs it and drafts with the paper link. Regenerate keeps the profile already chosen while it is still one of the paper's investigators, unless the first author now gets the link (`firstAuthorId` can be filled in after the draft, for example by the migration). The portal shows "Links to <name>'s profile (<reason>)." while the text still contains that profile link.
- Spotlight fields: the sync stores `teamMemberIds` (researcher `_id`s from provenance), `firstAuthorId` (the one team researcher matching the raw `authors[0]` via `normalizeAttributionAuthor` + `classifyResearcherAuthor`, including publication names and aliases; omitted when none or more than one match) and `paperAnchor` (`getPublicationAnchorId`, `paper-` plus the publication key made id-safe, in `lib/publicationIdentity.js`), all three built by `buildSocialPostTeamFields` in `lib/socialPostingServer.js`. `npm run migrate:social-posts` backfills them on records of any status that lack `teamMemberIds`, taking the team from the researchers the post names in `teamMembers` (cleaned, case-insensitive) rather than current provenance. It writes the three fields only when every recorded name matches a researcher: a partial `teamMemberIds` would stop later runs and the draft-time name matching, so a partly matched record is left for a later run once the names line up. A paper missing from the cache gets no `firstAuthorId` and an anchor from its GUID, and existing values are never overwritten. Older records not yet migrated fall back at draft time to matching `teamMembers` names and to the GUID anchor (`publicationAnchorFromKey`), with no first-author rule. Drafting writes `spotlightResearcherId`, `spotlightName`, `spotlightSlug`, `spotlightReason` and `postLink`, or unsets them when the post links to the paper; discard, dismiss and restore unset them with the draft. Each publication `<article>` in `app/publications/PublicationsBrowser.js` (used on `/publications` and profile pages) carries that anchor as its `id`. Papers sit inside closed year sections (`<details>`), which older Safari, including X's in-app browser on iPhone, does not open for a fragment link, so on load and on `hashchange` the browser component calls `revealLinkedPublication` (`lib/publicationIdentity.js`) to open the section holding a `#paper-…` target and scroll to it; other hashes are ignored.
- After each LLM draft, `checkSocialPostBody` in `lib/socialPostDrafting.js` looks for a missing investigator name, first-person wording, the journal name, and the post plus link exceeding X's 280-character weighted limit. Any problem triggers exactly one retry with the previous draft and the problem descriptions as feedback (and a shorter length target when length was the problem). If the retry still fails a check, or the model returns nothing, the post falls back to the template (`buildXPostText` in `lib/socialPosting.js`, which also names every investigator with the team label) and `generatedBy` is `template` instead of `llm:<model>`.
- Approvers can edit the system prompt itself (`SOCIAL_POST_SYSTEM_PROMPT` in `lib/summaries.js` is the built-in default) at `/admin/social`, in a collapsed "Drafting instructions (AI prompt)" section. The override is stored in its own singleton, `socialPostingPrompt` (fixed `_id`/`_type` `socialPostingPrompt`, every field read-only in Studio, edited only through the portal) — deliberately separate from `siteSettings` so a portal save can never collide with an unrelated Studio draft of `siteSettings`. `lib/socialPostingStore.js` has `fetchSocialPostPrompt` (published doc only), `saveSocialPostPrompt` and `resetSocialPostPrompt` (`create` on a missing doc, else a revision-guarded patch; a stale or missing revision on an already-edited doc maps to `error.conflict`, which the route turns into a 409). Sanity's `createIfNotExists` bumps `_rev` even when the document already exists, so never run it before an `ifRevisionId`-guarded patch on the same document. `resolveSocialPostSystemPrompt(custom, defaultPrompt)` in `lib/socialPosting.js` picks the trimmed custom text when there is one, else the default; `validateSocialPostPrompt` enforces non-empty and `SOCIAL_POST_PROMPT_MAX_LENGTH` (6000). The draft/regenerate route action resolves this effective prompt and passes it as `generateSocialPostText`'s `options.systemPrompt` (via `createSocialPostGenerateFn` in `lib/summaries.js`, factored out for testability) — the code-built user prompt (`buildSocialPostPrompt`) and every `checkSocialPostBody` check still always apply, whatever the custom prompt says. Editing the prompt does not require `postToX`, and does not change existing drafts, only the next Create post/Regenerate.
- Settings: `siteSettings.socialPosting.postToX` ("Offer new publications for X posts"; fail closed: off or unset makes dispatch return `skipped` and blocks drafting and queueing, while undo still works), `.teamLabel` ("Team name in posts", default `London Kidney`; replaced the old `xIntro` template-opening field), and `.approverEmails` (falls back to `studyApprovals.admins`). The settings query excludes Studio drafts.
- `BUFFER_API_KEY` is a Vercel server env var required for queue, undo and the status refresh; without it, queue and undo return a 500 and the portal skips the refresh. The free Buffer plan gives one key, 3,000 requests per 30 days and 10 queued posts per channel. Set the optional `BUFFER_X_CHANNEL_ID` only when more than one X channel is connected.
- Pure logic lives in `lib/socialPosting.js`, which must stay browser-safe because the portal imports it. `lib/socialPostingServer.js` holds the `node:crypto` helpers (document ids, email idempotency, notification dispatch), `lib/socialPostDrafting.js` writes drafts with the LLM function injected, and `lib/socialPostingStore.js` handles Sanity reads, writes and sync.
- Sanity Studio must be redeployed for the new `socialPost` statuses and fields (including the read-only profile-link fields above) and the Social Media Posting settings copy to appear there.

## People & Email Lists

- `/admin/people` replaces Sanity Studio for the email addresses staff maintain. - Each group edits its own settings: approval admins edit approval admins, coordinators, social post recipients and the contact addresses; update email admins edit update email admins and the mailing list. Any admin can view. The rules live in `PEOPLE_FIELDS` / `canEditPeopleField` in `lib/peopleSettings.js` (browser-safe, shared by page and API) and are enforced by `updatePeopleField` in `lib/peopleSettingsStore.js`, called from `app/api/admin/people/route.js` (GET/PATCH) with the access and email from the signed-in session, never from the request body.
- Every settings write sends the value the page started from (`previous`); a mismatch is a 409, and the patch carries `ifRevisionID`, so concurrent edits conflict instead of overwriting. Writes go to the published document and to its unpublished Studio draft when one exists (each guarded by its own revision), because publishing an older draft would otherwise undo the change and could quietly restore someone's access. Nested lists are written by merging into that document's own parent object (`studyApprovals`, `studyUpdates`, `socialPosting`), so sibling fields and a draft's other unpublished edits survive. Contact routing rewrites only the reasons whose address changed.
- An admin cannot remove their own address from approval admins or update email admins (`findEditorLockout`), so a group can never be emptied from the portal. Addresses outside the sign-in domains get a "Can't sign in" warning but are allowed, since they can still receive notification emails. Pasted text is parsed with `extractEmailAddresses`, which accepts Outlook "Name <address>; ..." lines and reports anything with an `@` that is not a valid address. Stored addresses are lowercased and deduplicated.
- Access changes take effect within a couple of minutes: `lib/auth.js` caches the lists for 60 seconds and the public Sanity client reads through the CDN. Portal edits appear in Sanity history as the API token, so each change is logged with the admin's email (`[people-admin]`, `[updates-admin-subscribers]`); subscriber addresses are kept out of those logs (record ids only).
- Mailing list edits go through `app/api/updates/admin/subscribers/route.js` (GET list, POST add, PATCH edit, DELETE; update admins only), with validation in `lib/subscriberAdmin.js` (browser-safe) and Sanity access in `lib/subscriberAdminStore.js`. Staff see one status (`active`, `suppressed`, `unsubscribed`) mapped onto `subscriptionStatus`/`deliveryStatus`; only `subscribed` counts as deliverable, matching the send routes. Adding someone, or resubscribing someone who unsubscribed, requires confirming that they asked for the emails (`consentConfirmed`); admin-added records get `source: admin`, a fresh `manageToken`, and the read-only `addedBy` field (Studio must be redeployed to show it). Duplicate addresses are refused case-insensitively. Edits send only changed fields, carry the record's `_rev`, and also patch its Studio draft; deletes remove both copies. The page nudges staff to unsubscribe rather than delete, so an opt-out record is kept. The CSV download prefixes cells that start with `= + - @` so a signup name cannot run as a spreadsheet formula.
- The list shows one row per person: the published record (its Studio draft, if any, is kept in step by every edit), or, for a record created in Studio but never published, the draft with the status `unpublished` ("Not published"). Those people get no emails and are left out of the counts. Staff review such a record and publish it (`action: publish` on the PATCH route, `publishSubscriber`), which needs the same consent confirmation as adding someone, validates the form like a new subscriber, and creates the published record under the draft's id while deleting the draft, keeping its token, creation date, consent record and send history. Unpublished records cannot be edited in place, and adding an address held only by one points staff to it instead of creating a second record.

## Data Refresh

- PubMed cache file: `runtime/pubmed-cache.json` with lock/cancel files.
- If cache changes are needed, use the scripts rather than editing files directly.
- Research digest PubMed scanning uses a curated journal whitelist and PubMed entry date windows through `lib/researchDigest.js`; do not merge it with the KCRU-authored publication cache unless product requirements change.
- Automatic paper selection requires `triageStatus == "include"`, no triage error, complete summary copy, an allowed publication type, and a conservative priority score at or above the configured threshold. Never fill the daily quota with weak papers.
- Research digest opportunity feeds import to pending `researchOpportunity` documents; public pages and email must query only approved rows.
- The scheduled research digest import workflow requires `NEXT_PUBLIC_SANITY_PROJECT_ID`, `NEXT_PUBLIC_SANITY_DATASET`, and `SANITY_API_TOKEN`; include the selected LLM provider secret and `PUBMED_API_KEY` as GitHub Actions secrets.
- Missing publication tags can be rebuilt without refetching PubMed by writing `pubmedClassification` docs via `npm run reclassify:pubmed`; use `--year=YYYY` for targeted backfills.
- The scheduled publication refresh also discovers recent DOI-registered journal articles through Crossref, OpenAlex, and Europe PMC. Crossref uses researcher ORCID where deposited plus a strictly validated author-name query; OpenAlex and Europe PMC discovery require the researcher ORCID stored in Sanity. Preprints are not imported by this path.
- Researchers with namesakes can use `publicationAuthorName` to reject an explicitly conflicting middle initial and `publicationExclusions` for verified false-positive PMIDs or DOIs. A missing middle initial must remain eligible. Verified alternative full names belong in `publicationAuthorAliases` (Other Publication Names in Studio); do not infer nicknames or different full given names from a shared initial. Apply exclusions per researcher so legitimate consortium papers attributed to other KCRU researchers remain available.
- Publications use a normalized DOI as their canonical identity when available, with PMID as the fallback. This lets an early DOI-only record merge into the later PubMed record without creating a duplicate.
- PubMed DOI extraction must prefer the typed `articleids` DOI. Its `elocationid` can mix a PII and DOI; normalize only the DOI token and use PMID when none exists. Cache reads merge normalized identities and combine their researcher provenance, and the next refresh rewrites legacy identifiers.
- Supplementary attachments (for example, Figshare `Additional file 1 of ...`, including versioned DOIs) are excluded by `isPublicationSupplementaryMaterial` before secondary-source attribution and summaries, on public reads, and during retention. Repository metadata calling a supplement a journal article must not bypass this rule.
- Publication attribution review is controlled by the fail-closed `siteSettings.publicationAttributionReview.enabled` setting. Missing or false keeps legacy discovery behavior while continuing to respect each researcher's `publicationExclusions`.
- When attribution review is enabled, `publicationAttributionReview` documents store deterministic researcher-plus-DOI/PMID decisions and normalized candidate snapshots. A researcher-specific PubMed search hit must have a compatible indexed author or investigator name before it can publish automatically or contribute coauthor evidence. PubMed may broaden a malformed name query into general terms plus a surname; use surname-first author queries and inspect the returned query translation when changing them. Exact ORCID also requires a compatible name. Ambiguous links from any source remain pending and outside public provenance. A recurring coauthor must occur on at least two confirmed PubMed papers, counting a person once per paper and excluding investigator lists from coauthor counts. An ORCID counts as exact identity evidence only when it comes from PubMed, Crossref or Europe PMC (`orcidSource` on each structured author; untagged authors inherit the publication `source`). OpenAlex derives author ORCIDs from merged author profiles that absorb namesakes (on 2026-09-28 it auto-confirmed Mount Sinai, Terumo India, Intermountain Health and Guizhou papers for team researchers), so an OpenAlex ORCID match is held for review unless a compatible author entry carries a known affiliation of the researcher or the recurring-coauthor rules confirm it. A conflicting ORCID likewise counts only from a verified source: OpenAlex gave Amit Garg a different ORCID on a genuine trial paper, which must not hold a paper that affiliation and recurring coauthors corroborate.
- After discovery, `sweepCoauthorAttributions` (`lib/publicationAttributionReview.js`) checks every returned paper for team researchers not yet attributed, because a paper found for one researcher may list another whose own queries missed it (no ORCID on file, an affiliation-restricted PubMed query, or a common name the Crossref name query cannot surface). The coauthor is evaluated with the secondary-evidence rules and never as a PubMed-confirmed hit: confirmed links join the provenance, uncertain ones become pending reviews, and excluded, rejected, or degraded-researcher pairs are skipped. Pairs already in the previous cache are evaluated too, because a run's own provenance replaces the cached one for every paper it returns (`retainPublications` consults the cached provenance only for papers the run did not return), so a sweep-added link must be re-confirmed each run to survive; a hold on such a pair creates no review, so the sweep never pulls a live link into review. Only byline authors count as coauthors; an investigator-list appearance is left to the researcher's own PubMed query (add `[Investigator]` there, as Amit Garg's query does), because those candidates would carry hundreds of contributors in their snapshots. The run log lists every pair the sweep evaluated with its decision. Disable with `PUBLICATION_COAUTHOR_SWEEP=false`.
- `upsertPublicationAttributionCandidates` refreshes every review document for a paper the run returned, and each candidate travels twice in the mutation (create-if-missing plus the refresh patch). Sanity rejects request bodies over 4,000,000 bytes (`httpRequestEntityTooLargeError`), and snapshots holding a trial's investigator list reach 170 KB each, so the upsert commits in size-bounded batches (`DEFAULT_ATTRIBUTION_MUTATION_BYTES`). On 2026-09-29 the first coauthor sweep pushed the single-transaction upsert past the limit and the refresh failed before writing the cache; never collapse the batches back into one transaction.
- Sanity Studio must be redeployed for the review evidence fields `hasUnverifiedOrcid` and `matchedOrcidSource` and the snapshot author field `orcidSource` to show there; the app reads and writes them regardless.
- PubMed attribution retains indexed `InvestigatorList` collaborators and compact initials such as `MA`, including contributors absent from the displayed byline. Keep this evidence through review snapshots without adding it to the large public cache. Reload reviews after discovery and exclude pending as well as rejected links before cache retention, so yesterday's cache cannot restore an attribution held by today's run.
- Discard unequivocal author-name mismatches before creating review candidates: William Weir, Christopher Weir, or Matthew R Weir cannot match Matthew A Weir. Check all indexed authors, collaborators, and configured aliases first; missing given names, absent contributor metadata, and compatible abbreviated names remain eligible for review. Carry automatic rejections through cache retention without creating pending reviews or overwriting a prior manual decision.
- When a secondary source also supplies a paper available in the current PubMed batch, use PubMed's structured author and collaborator metadata for vetting. Secondary author clusters can substitute another person's name or omit collaborators; they must not turn an independently confirmed PubMed attribution into a pending review.
- Keep structured author, ORCID, affiliation, query-path, and coauthor evidence through each attribution decision and in review snapshots, but do not copy it into the large `pubmedCache` singleton. Persisting that evidence for every publication can exceed Sanity's mutation-size limit.
- Approval admins review candidates at `/admin/publications` through `/api/publications/attribution-review`. Approvals publish on the next refresh; rejections also add a researcher-specific exclusion. Reversing a rejection removes that exclusion. Refresh upserts may update candidate metadata but must never overwrite an approved or rejected decision.
- Approved review snapshots are part of discovery recovery so manual decisions survive source outages. Rejected or excluded researcher links must be removed before retention; if no valid researcher remains, the publication leaves the public cache, while multi-researcher papers keep their other valid links.
- After each GitHub Actions PubMed refresh, `/api/publications/attribution-review/dispatch` sends one CRON-authenticated batched email to `siteSettings.studyApprovals.admins` for new pending candidates and seven-day reminders. Resend stays in the deployed environment. Failed or skipped delivery must not advance notification tracking; the endpoint supports authenticated `dryRun` selection without sending.
- The reviewed 2026-08-25 baseline migration is `npm run migrate:publication-attribution` (dry run) and the same command with `-- --apply`. It is locked to cache timestamp `2026-08-25T09:42:28.404Z`, 446 publications, 636 active links, 53 approvals, and one Danielle Nash rejection; do not relax those guards or enable the gate before the atomic seed/correction transaction is ready.
- Letter exchanges are excluded by rule in `lib/publicationExclusions.js` (`isPublicationCorrespondence`): a record PubMed types as `Comment` (letters to the editor, authors' replies, editorials about one paper) with no genuine abstract, or whose title reads as a reply (`Reply to:`, `Authors' reply`, `Re:`, `Letter to the Editor`, `Comment on`). Publisher `article_body` text from the DOI backfill does not count as an abstract, and the backfill skips excluded records. `Letter` alone is not a signal: JAMA- and AJKD-style research letters have no abstract and must stay. A `Comment`-typed piece with a real abstract is kept. The rule runs wherever `isPublicationExcluded` runs (cache read, refresh, pages, newsletter), so it applies to already-cached rows without a refresh.
- Secondary-only discoveries are published only after usable source text is found. A missing abstract from one source always falls through to the next source; after all abstract sources are exhausted, substantive publisher article body text is accepted as the final fallback. Records with neither are rediscovered and retried by the next scheduled refresh.
- Scheduled PubMed refresh now runs from `.github/workflows/pubmed-refresh.yml` via `npm run refresh:pubmed`, not from Vercel cron. The workflow writes directly to Sanity, then calls `/api/pubmed/revalidate` to refresh cached public pages.
- The PubMed GitHub Actions workflow requires repo secrets for `NEXT_PUBLIC_SANITY_PROJECT_ID`, `NEXT_PUBLIC_SANITY_DATASET`, `SANITY_API_TOKEN`, `SITE_URL`, and `CRON_SECRET`; add the selected LLM provider API key there too.
- The model default lives in one place, `DEFAULT_LLM_MODEL` in `lib/summaries.js`. Sanity `llmModel` and `trialSummaryLlmModel` are the roots of every per-task chain; the other model fields inherit from them when blank, so changing those two changes every task. `trialSummaryLlmModel` shadows `llmModel` for all trial work — updating only `llmModel` leaves trial paths on the old model.
- Reasoning effort is requested for every task via `OPENROUTER_REASONING` and gated by an allowlist of reasoning-capable model families. The allowlist matches later versions within a family so a model bump cannot silently drop reasoning; a test asserts `DEFAULT_LLM_MODEL` is covered. Never narrow that pattern to a single version.
- **Reasoning tokens are drawn from `max_tokens`.** At high effort a model can spend the whole budget thinking and return an empty body (`finish_reason: length`), which arrives as a JSON parse failure, exhausts the retries and drops the publication's summary entirely — and it fails hardest on the papers needing the most reasoning. `resolveCompletionBudget` adds `REASONING_TOKEN_HEADROOM` on top of the caller's content budget whenever reasoning is sent. Do not remove it when tuning token limits.
- If summary-eligible publications remain but no credential is available for the configured LLM provider, the PubMed refresh script now fails the workflow instead of silently skipping summary generation.
- Publication summary generation expects structured JSON with `summary`, `topics`, `study_design`, `methodological_focus`, and `exclude`; keep the parser tolerant of OpenRouter/Gemini variants that may return JSON-like content inside the `summary` field, and preserve recovered classification tags rather than displaying raw JSON.
- Hosted Studio refresh controls must open GitHub Actions workflows instead of posting shared bearer tokens from the browser. Direct `/api/pubmed/refresh` runs remain appropriate for localhost/dev-server or server-side use where Vercel time limits do not apply.
- Sanity Studio includes a Site Settings action that opens the server-side PubMed/SEO GitHub Actions workflow; do not add a browser-side SEO refresh token.
- The hosted Studio is published by `.github/workflows/sanity-studio-deploy.yml` (manual `workflow_dispatch`; run it after any schema change). It reads the project and dataset from the `NEXT_PUBLIC_SANITY_*` secrets and authenticates with `SANITY_DEPLOY_TOKEN` (a Sanity token with the Deploy Studio permission), falling back to `SANITY_API_TOKEN`. It installs `@rollup/rollup-linux-x64-gnu` without saving because the lockfile omits Rollup's Linux binary (npm/cli#4828); `npx sanity build` fails without it on Linux.
- DOI publication-text backfill (`lib/doiAbstract.js`) uses an ordered fallback: (1) plain fetch of publisher abstract meta tags, (2) Crossref API, (3) OpenAlex inverted-index abstract, (4) Europe PMC core metadata, and (5) headless Chromium for publisher abstract metadata/sections. If those all miss, the publisher-page fallback extracts substantive article body text from an explicit article/full-text container in rendered or plain HTML. Saved text is labeled as `abstract` or `article_body`, and a later true abstract replaces body text even when it is shorter.
- When the publisher page has neither an abstract nor article text (paywalled editorials, commentaries and letters whose opening page is shown only as an image, such as SAGE's Peritoneal Dialysis International editorials), `lib/publisherFirstPage.js` locates the first-page preview image and the configured summary model transcribes it (`transcribePublicationPageImage` in `lib/summaries.js`, minimal reasoning effort, image sent inline as base64). The text is saved as `article_body` with `abstractSource` set to `publisher first page image` (`PUBLISHER_FIRST_PAGE_SOURCE` in `lib/publicationIdentity.js`), so it never counts as a genuine abstract for the correspondence exclusion, and the summary prompt is told that only the opening page was available. The step runs last, only for non-excluded DOI candidates after every text source misses, once per DOI per retry interval, and only when the summary provider has a credential (`createPublicationPageTranscriber`); the image request falls back to the headless browser (`browserFetchBytes`) when the plain fetch is refused. Ollama is not wired for image input.
- Publisher and configured-feed fetches must pass `lib/outboundUrlSafety.js`: HTTPS only, public DNS addresses only, manual validation of every redirect, and bounded response bodies. Chromium subrequests must preserve the same public-network checks and work budgets.
- Headless browser uses `puppeteer-core` + `@sparticuz/chromium-min` on Vercel and local/system Chrome elsewhere. It is enabled by default on Vercel and explicitly enabled in the scheduled GitHub Actions refresh; set `DOI_BROWSER_FETCH=true` for other environments or `DOI_BROWSER_FETCH=false` to disable.
- OpenAlex discovery works without credentials; `OPENALEX_API_KEY` only raises the rate limit, so never gate discovery on it. OpenAlex sort parameters use `field:direction` (`publication_date:desc`) — a leading hyphen is parsed as part of the field name and rejects the whole request with `400 Invalid query parameters`.
- OpenAlex discovery skips works whose `primary_location.source.type` is `repository` (institutional-repository copies such as `10.17615/…` and `10.5167/uzh-…` carry their own DOI, so the DOI identity cannot merge them and the paper would show twice). The journal version arrives through PubMed or Crossref.
- Set `CROSSREF_MAILTO` (and optionally `PUBMED_API_KEY`) as GitHub Actions secrets so scheduled refreshes use the Crossref polite pool and PubMed's higher rate limit. Without them, Crossref returns `429` for a varying subset of researchers on every run.
- Discovery-source requests retry throttled and transient failures (`lib/secondaryPublications.js`), and every remaining failure is reported through `onSourceError` so the refresh knows which researchers came back incomplete.
- Publication membership is sticky (`lib/publicationRetention.js`). A cached publication that a refresh does not return is carried forward with its summary, classification and provenance intact, and is only pruned after `PUBLICATION_PRUNE_AFTER_MISSING_RUNS` (default 3) consecutive runs in which discovery for its attributed researchers actually succeeded. Never reintroduce a code path that treats a single run's result set as authoritative — transient upstream failures used to delete published papers from the site.
- Both packages are listed in `serverExternalPackages` in `next.config.js` to prevent bundling.

## Classification Model Evaluation (Jev)

- Jev (TypeSafe AI's "System One" decision model) can classify publications instead of the chat model. Which system runs is a staff setting, `siteSettings.publicationClassification.backend` (`chat`, the default, or `jev`), read by `resolvePublicationClassificationSettings` in `lib/classificationSettings.js` and passed as `llmOptions.classification` by every refresh entry point (`scripts/refresh-pubmed-cache.js`, `/api/pubmed/refresh`, `/api/pubmed/summarize`) and by `runPubmedReclassification` (override per run with `--backend=jev|chat`). Both paths call `classifyPublicationWithBackend` in `lib/classificationBackend.js`.
- With `backend: jev`, the refresh path still makes its combined chat call for the lay summary, then replaces the chat model's tags with Jev's (`classifySummarizedWithJev` in `lib/publications.js`); if Jev fails for a paper, the chat tags from that same call are kept. The no-abstract loop and the reclassify path have no prior chat call, so there a Jev failure falls back to a chat classification and the stored `pubmedClassification` document records `backend: "chat (fallback from jev)"`. Jev-classified documents record `provider` as the transport and `model` as the Jev model.
- `lib/jevClient.js` speaks TypeSafe's `POST /v1/systemone` wire format (mirrors `@typesafe-ai/sdk` 0.6.0 without adding the dependency). Transport is `typesafe` (`TYPESAFE_API_KEY`, model `jev-latest`) or `openrouter` (`OPENROUTER_API_KEY`, model `typesafe/jev-1.13`, endpoint `/api/alpha/decisions` - Jev is rejected by chat completions and is absent from the public models list). OpenRouter is the default (no new credential needed); a `TYPESAFE_API_KEY` switches to the direct API. Override with `JEV_TRANSPORT` and `JEV_MODEL`.
- `lib/jevClassifier.js` asks one yes/no ("noul") question per canonical tag plus one for `exclude` - 46 questions in a single request per paper - and gets a calibrated probability for each. Question criteria are parsed from the taxonomy tables in `lib/classificationPrompt.js`, so editing a tag's table row changes both systems; a test asserts every canonical tag has a row. The questions are the bulk of each request (roughly 8k input tokens per paper regardless of abstract length).
- The canonical tag lists moved to `lib/classificationTaxonomy.js`, which is browser-safe; `lib/summaries.js` imports `enforceCanonicalCategories` from there. `app/publications/PublicationsBrowser.js` still carries its own copy.
- Jev scores each tag in isolation, so cross-tag rules the prompt states in prose are enforced in code for the Jev path only (`applyClassificationPrecedence`): general "Chronic Kidney Disease" yields to a specific cause or modality tag (`CKD_SUPERSEDING_TOPICS`), and "Survey Research" implies "Observational Study". Add further prose rules there and quote the prompt sentence they enforce.
- Thresholds resolve Sanity (`publicationClassification.jevThreshold*`) over env (`JEV_THRESHOLD_TOPICS`, `JEV_THRESHOLD_STUDY_DESIGN`, `JEV_THRESHOLD_METHODOLOGICAL_FOCUS`, `JEV_THRESHOLD_EXCLUDE`) over the 0.5 defaults (`lib/jevDecisions.js`). The intended way to set them is `/admin/classification-eval`: evaluation runs start from the production thresholds, the sliders re-cut the stored probabilities in the browser, and "Use these thresholds in production" writes them to Site Settings with the run they came from and who applied them. The classifier is switched from the same page (Production classifier card; refused when no Jev credential is configured, since every paper would fall back to chat) or in Studio (Site Settings → Publication Classification); the block records who switched it and when. Sanity Studio must be redeployed for the new fields to show there; the app reads and writes them regardless.
- Run an evaluation with `npm run eval:jev-classification -- --count=50 --seed=1` (also `--year=`, `--pmids=`, `--label=`, `--dry-run`, `--no-persist`, `--out=file.json`) or from `/admin/classification-eval`, whose route is capped at 100 papers because it runs inside one request. Runs are stored as `classificationEvalRun` documents (`lib/classificationEval.js`). The sample is a seeded shuffle of cached publications that have an abstract of at least 50 characters and a stored classification (a `pubmedClassification` document is preferred because it records the model; cache tags are used otherwise), so the same seed reproduces the same papers. The `exclude` comparison applies the publication-type correction rule to Jev's answer, as the reclassification path does for the chat model.
- The stored classification is the comparison reference, not ground truth: a disagreement means one of the two systems is wrong. Decide from the per-paper view before changing thresholds, precedence rules, or prompt criteria.
- Pre-existing gap, left as is: the refresh entry points pass only the summary provider/model/system prompt into `llmOptions`, so the combined summary+classification call ignores `llmClassificationProvider`, `llmClassificationModel` and a Sanity-edited `llmClassificationPrompt`; only `runPubmedReclassification` and `/api/pubmed/classify-preview` honour them. Jev in the refresh path therefore builds its questions from the built-in prompt, matching the chat call beside it.

## Cron Jobs

- Scheduled routes are defined in `vercel.json`.
- PubMed refresh scheduling uses GitHub Actions (`.github/workflows/pubmed-refresh.yml`) rather than `vercel.json`. Manual app refreshes still use `/api/pubmed/refresh` with `PUBMED_REFRESH_TOKEN`, and post-refresh cache invalidation uses `/api/pubmed/revalidate` with `CRON_SECRET` or `PUBMED_REFRESH_TOKEN`.
- Scheduled workflows that spend money are gated on a repository variable so they can be switched off without editing YAML: `RESEARCH_DIGEST_ENABLED` for the research digest (LLM triage over every candidate paper) and `SEO_REFRESH_ON_PUBMED_CRON` for the SEO snapshot step. Set them with `gh variable set NAME --body true|false`. Anything other than `true` leaves the schedule paused, so an unset or mistyped value fails safe. Manual `workflow_dispatch` runs deliberately ignore these gates. Prefer this pattern over commenting out a `cron:` entry — it keeps the schedule visible and makes the on/off state a one-command change.
- The PubMed workflow runs at `09:00 UTC`, before the `11:00 UTC` newsletter workflows, and uses a GitHub Actions concurrency group to avoid overlapping refresh runs.
- `/api/seo/refresh` auto-generates SEO/LLM summaries and snapshots publication topics/highlights for llms.txt/markdown (manual via `SEO_REFRESH_TOKEN`; requires `SANITY_API_TOKEN`). Scheduled PubMed refreshes follow the `SEO_REFRESH_ON_PUBMED_CRON` variable, while manual `workflow_dispatch` runs only refresh SEO when their `run_seo_refresh` input is enabled.
- Study email scheduling uses GitHub Actions rather than `vercel.json`; scheduled runs authenticate with `CRON_SECRET` and flow through the route's nth-weekday guard.
- Publication newsletter scheduling uses GitHub Actions rather than `vercel.json`; scheduled runs authenticate with `CRON_SECRET` and flow through the route's nth-weekday guard.
- Research digest scheduling uses GitHub Actions rather than `vercel.json`; import runs inside GitHub Actions via `npm run import:research-digest` to avoid deployed route timeouts, and dispatch sends only to active subscribers who explicitly selected `research_digest`. Partial delivery keeps the issue retryable and makes the workflow fail visibly.
- Shared nth-weekday scheduling helpers live in `lib/cronUtils.js`.

## Dependency Upgrades

- **Pin `next` to an exact version** in `package.json` (no `^` or `~`). Turbopack regressions in minor releases have caused production-wide 500 errors on all server-rendered pages. Only upgrade Next.js intentionally, test the build, and verify at least one dynamic page works locally before pushing.
- After upgrading Next.js, check every dynamic page (`ƒ` in build output) locally — static/ISR pages can mask server-rendering crashes because they are served from cache.
- `next-auth` v4 is not officially compatible with Next.js 16+; it works today but may break on future upgrades. Plan to migrate to Auth.js v5 when practical.
- `puppeteer-core` and `@sparticuz/chromium-min` are large native packages. They must stay in `serverExternalPackages` in `next.config.js` and should only be imported dynamically (via `await import(...)`) to avoid cold-start and bundling issues.
- In Next.js 15+ (and enforced in 16), `params` and `searchParams` page props are Promises. Always `await` them before accessing properties — synchronous access will crash in production even if it appears to work in dev.
